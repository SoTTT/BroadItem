# 运行期诊断状态与模板可变状态专项设计（草案）

> 源起：土法编程审阅 #9/#10/#13 逐条讨论时发现三者是同一设计问题的表象——
> **"模板只读共享"（#5 承重墙）与"模板级跨管线状态"之间存在未被正视的矛盾**，
> 且运行期诊断上下文无一等公民对象承载，状态被涂抹到全局栈、模板 mutable 成员与
> 人工安装纪律三处。本文给出治本设计，合并解决 #9（线程假设）、#10（去重状态错位）、
> #13（RuntimeScope 人工安装），顺带收编 ImageElement 的模板级 mutable 缓存。
>
> 状态：**已按裁决实施（2026-08）**：①去重窗口 Frame 实例级；②ImageElement 缓存一并迁出；
> ③直调 LayoutEngine 接受"无 scope 不去重"写入文档。双栈 ctest 18/18。

## 1. 问题（现状证据）

### 1.1 矛盾一：模板只读 vs 模板级可变状态

模板层 `Element` 树 parse 后不可变、可安全共享，`ConstElementPtr` 贯穿共享边界
（doc/模板只读边界.md）。但同一模板上开着三个 `mutable` 口子：

- `Element::m_reportedDiagnostics`（Element.h:250）：运行时诊断去重集合，
  注释自认"仅模板根元素的集合被使用"——N 个节点白背 N-1 个永远为空的 QSet；
- `ImageElement::m_pixmapCache` / `m_failedPaths`（ImageElement.h:47-48）：
  模板级图像成功/失败缓存。

`mutable` + "依赖 GUI 单线程假设"注释把矛盾糊住；多线程摸同一模板时全部为数据竞争
（C1：去重集合 `contains`→`insert` 两步非原子，QSet rehash 期间并发读 = UB）。

### 1.2 矛盾二：运行期上下文无一等对象

"当前管线跑在哪棵模板上"没有对象承载，经全局栈隐式传递：

- `runtimeStack()`（Diagnostics.cpp:128-132，函数级 static vector）传模板根指针；
- `RuntimeScope`（Diagnostics.h:101-115）仅 RAII 压/弹栈，自身不持状态；
- 安装靠 Frame 人工接线（Frame.cpp:151、:184 两处）；直调 LayoutEngine 的调用方
  无 scope，`reportRuntime` 栈空则跳过去重照报（Diagnostics.cpp:184）——
  去重语义随调用路径分叉，无提示（#13）。

同构的 `sessionStack()`（Diagnostics.cpp:121-125，ParseSession 栈）承担解析期上下文，
同样全进程一份。

### 1.3 症状-根因映射

| 审阅项 | 表象 | 根因 |
|---|---|---|
| #9 | 全局状态单线程假设仅注释标明 | 矛盾二（全局栈）+ 矛盾一（模板 mutable） |
| #10 | 去重集合挂每个 Element、key 土法拼接 | 矛盾一（状态住在模板里） |
| #13 | RuntimeScope 人工安装，直调静默失去去重 | 矛盾二（无一等对象，靠纪律接线） |
| C1 | 共享模板根上 mutable QSet 并发读写 | 矛盾一 |

### 1.4 附带：其余无防护全局状态（#9 清查结论）

- `processCollector()`（Diagnostics.cpp:114-118）：`setCollector` 写 / report 读，
  shared_ptr 裸读写竞争；
- `LayoutRegistry::m_layouts` / `m_nextId`（LayoutRegistry.h:28-29）：并发注册/查询/ID 分配竞争。

## 2. 设计

### 2.1 核心决策：去重状态的所有权归 Frame（去重窗口语义变化）

现状语义（设计.md:1023）：同一（**模板** × 错误码 × 绑定路径）只报告一次，
窗口 = 模板生命周期，跨实例共享。

**草案推荐改为：去重状态由 `Frame` 持有**（成员 `m_reportedDiagnostics`），
窗口 = Frame 实例生命周期。理由：

- 防刷屏目标（秒级刷新下同一错误反复投递）完全达成——重布局总是经同一 Frame；
- 状态随 Frame 单线程使用（GUI 线程），**共享消失，C1 竞争连根消除**，无需锁；
- 无悬空的模板指针键问题（旁置表方案需 weak_ptr + 过期清理，见 2.6 对比）；
- 语义上更真实：错误往往源自实例数据，"每个可见实例报一次"比"50 实例共报一次"
  更利于定位。

代价（须确认接受）：同一模板 N 个实例各报一次（N 份而非 1 份）。
设计.md:1023 的"模板 × 错误码 × 绑定路径"措辞需同步修订为"实例（Frame）级"。

### 2.2 部件改动

**Element 去 mutable**：

- 删除 `m_reportedDiagnostics` 成员与 `markDiagnosticReported()`（公共 API 移除，
  0.x 阶段跨 minor 允许调整，发布注记说明）；
- 模板回到完全只读，`ConstElementPtr` 承重墙不再有洞。

**诊断键结构化**：

```cpp
/// @brief 运行时诊断去重键（取代 codeToString(code) + '|' + bindingPath 拼接）。
struct DiagnosticKey {
    ErrorCode code;
    QString bindingPath;
    bool operator==(const DiagnosticKey& o) const { return code == o.code && bindingPath == o.bindingPath; }
};
uint qHash(const DiagnosticKey& k);
```

**RuntimeScope 改持状态指针**（不再是"根指针 + 全局栈"的间接寻址）：

```cpp
class RuntimeScope {
public:
    explicit RuntimeScope(QSet<DiagnosticKey>* dedupState);  // 由 Frame 成员传入
    ~RuntimeScope();
private:
    QSet<DiagnosticKey>* m_state;   // 不持有；栈顶即当前去重状态
};
```

`reportRuntime` 判决逻辑不变，仅"问栈顶 scope 的集合"替代"问栈顶根的成员"。

**Frame**：新增成员 `QSet<DiagnosticKey> m_reportedDiagnostics;`，
`performLayout`/`paint` 的安装点改为 `RuntimeScope scope(&m_reportedDiagnostics);`——
Frame 构造即天然持有状态，"忘记安装"的失败模式在结构上只剩"忘记写 scope 那行"，
且该行为 Frame 内部两处，不外溢（#13 对正规管线闭环）。

### 2.3 线程模型（#9 硬化）

| 状态 | 手段 | 说明 |
|---|---|---|
| `sessionStack()` / `runtimeStack()` | **thread_local** | 栈语义跨线程必串线（锁修不好），TLS 后每线程各一条，多线程 parse/管线语义正确 |
| `processCollector()` | **一把互斥锁** | 锁内拷贝 shared_ptr、锁外调 `report()`（防用户收集器回调 Diagnostics 重入死锁） |
| `LayoutRegistry::m_layouts` + `m_nextId` | **一把互斥锁** | 注册/查询/ID 分配同进同出；非热路径，QMutex 即可 |
| Frame 持有的去重集合 | **无需锁** | Frame 单线程使用前提（GUI 栈固有），文档声明 |

### 2.4 ImageElement 缓存收编：路径键进程级缓存

`m_pixmapCache`/`m_failedPaths` 的键是**文件路径**——同路径同图，与模板本无必然绑定。
收编为 diagnostics 外的独立进程级缓存（`src/element/image/` 内部单元，
`QHash<QString, QPixmap>` + `QSet<QString>` + 一把互斥锁）：

- ImageElement 的 mutable 成员清零，模板全树真正只读；
- 缓存跨模板共享（顺带收益：多模板引用同图不再重复加载）；
- 单点锁，加载非热路径，开销可忽略；
- 缓存永不淘汰的语义保持（与现状一致，生命周期从"随模板"变"随进程"，差异可忽略——
  模板一般也随进程）。

### 2.5 直调 LayoutEngine 场景（#13 残余面）

测试 helpers 等直调方没有 Frame。提供两个选择：

- 显式自理：自建 `QSet<DiagnosticKey>` + `RuntimeScope`（API 公开即可）；
- 文档声明：无 scope 时 `reportRuntime` 不去重照报（现状行为），
  在设计.md 诊断节写明"去重仅存在于 Frame 管线"。

**不引入** LayoutEngine 相位级自动 scope（每相位独立去重窗口语义混乱，收益存疑）。

### 2.6 备选方案对比（为何不选旁置表）

模板级窗口的保真方案是 Diagnostics 持 `QHash<模板根, 已报集合>` 旁置表：
模板非 QObject 无销毁信号，须 `weak_ptr` 键 + 定期清理过期条目，且多线程仍需锁表。
复杂度（弱键清理 + 锁）显著高于 Frame 持有，唯一收益是保住"N 实例共报一次"。
仅当 2.1 的语义裁决坚持模板级窗口时采用。

### 2.7 明确不动的部分

- `ParseSession` 的职责划分（元素路径、sawAbort）不变，仅栈载体 TLS 化；
- `ErrorCollector` 接口、码表、消息格式不变；
- 默认收集器 qWarning/qCritical 转发行为不变；
- `LayoutContext`（数据上下文）不变——本设计不碰绑定求值路径。

## 3. 行为不变量

- 单线程现有全部行为不变：去重命中/未命中、Abort 语义、元素路径格式；
- 唯一语义变化：跨实例去重窗口（2.1，须经裁决确认）；
- 双栈 ctest 18/18 为基线；`test_diagnostics` 的运行时去重用例按新窗口语义修订。

## 5. 待裁决点（已定，2026-08）

1. **去重窗口**：Frame 实例级（推荐）vs 模板级（旁置表 + weak_ptr，复杂度高）。
   前者改设计.md 语义措辞，后者保措辞但付实现复杂度。
   **→ 已定：Frame 实例级**，设计.md 措辞已同步修订。
2. **ImageElement 缓存**是否随本次一并迁出（推荐一并，模板 mutable 一次清零）；
   或仅修诊断集合、缓存留待下回。
   **→ 已定：一并迁出**（进程级 ImageCache + 互斥锁）。
3. **直调 LayoutEngine** 是否接受"无 scope 不去重"写入文档了事（推荐），
   或要求相位级保底去重。
   **→ 已定：接受并文档化**（Diagnostics.h 与本文 2.5 均已声明）。
