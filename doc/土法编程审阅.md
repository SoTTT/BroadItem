## #1 路径语法两套实现，索引解析三处逐字重复

- **现状**：
  - 解析期：`src/expression/Expression.cpp:15-93` 游标状态机（校验 + 分段），95 行。
  - 运行期：`src/context/PropertyContext.cpp` 另一套游标逻辑——`walkNested`（6-53）、`setWalkInto`（90-194，105 行超长函数）、`advanceBrackets`（197-235）。
  - `[n]` 索引处理块（`indexOf(']')`→`toInt`→负值/越界报错）约 25 行三处近乎逐字重复（PropertyContext.cpp:97-129 vs 201-231 等）。
  - `MapPropertyContext::resolveFirstThenWalk`（MapPropertyContext.h:106-131）与 `PropertyContext::walkPathFromObject`（PropertyContext.cpp:56-87）前奏同构复制；`setPropertyNested` 在 MapPropertyContext.h:80-101 与 QPropertyContext.cpp:119-154 成对重复。
  - 漂移风险实在：Expression 拒绝的语法（如前导 `[`）walker 侧各自判断，两边可静默分叉。
- **方向**：让"分段序列"成为唯一中间表示——解析一次，walker 消费分段而非字符串游标。
- **安全网**：`test_expression` + `test_property_context` 覆盖充分。

### 结论（2026-08，已实施）

选根治方案（讨论中确认两个分歧今天就存在：`a.` 解析期非法/运行期静默接受；`a[0]b` 解析期合法/运行期必报错）：

- `Expression` 升级为唯一语法权威：产出类型化分段 `PathSegment{key | index}`，语法规则成文于类注释并收紧（`a[0]b`、`a.`、`a[0].` 均判非法）；
- `PropertyContext` 三个 walker 合并为 `walkSegments`/`setWalkSegments`（消费分段），`segmentEnd`/`advanceBrackets`/`setWalkInto`/手写 `[n]` 块全部删除；
- `MapPropertyContext`/`QPropertyContext` 入口统一先过 `Expression`；
- 附带收编 #14：前缀匹配唯一实现迁入 `Expression::pathMatches()`；
- 测试：`test_expression` 迁到类型化分段并新增三个收紧用例，`test_property_context` 新增运行期病态路径回归。双栈 ctest 18/18。

## #4 对齐取值 stringly-typed

- **现状**：`"center"/"end"/"start"/"stretch"/"baseline"/"right"/"bottom"` 等取值裸 QString 存储 + 字符串比较分发，27 处散于 4 文件（TextElement.cpp 11、LinearLayoutCommon.cpp 10、CellElement.cpp 4、LinearLayoutCommon.h 2）。非法取值静默落 default 分支，无解析期校验。`TextElement::render` 内 284-289 与 310-313 对 `m_hAlign` 同函数重复三分支。
- **方向**：枚举化 + 解析期校验（与 BI-P-015/016 诊断体系气质一致）。

### 结论（2026-08，已实施）

选枚举化根治方案。讨论中确认问题最实的一处：非法 `cross-align` 静默兜底为 start 行为，而 XSD 默认是 stretch——拼写错误直接改变布局且无任何提示。

- **枚举权威**：新增公共头 `include/broaditem/element/Alignment.h`——`HAlign`/`VAlign`/`MainAlign`/`CrossAlign` 四枚举（baseline 并入 CrossAlign，仅 row 合法）+ `hAligned()`/`vAligned()` 几何映射 inline + 解析助手 `parseHAlign()` 等（实现 `src/element/Alignment.cpp`）。
- **解析期校验**：非法取值报新码 **BI-P-024**（Error/Default，属性保持默认值）；column 的 `cross-align="baseline"` 从静默退化改为解析期拒绝（`parseAttributes` 按轴判定）。
- **消费侧枚举化**：TextElement/CellElement/ColumnLayout/RowLayout 成员改枚举；27 处字符串比较全部消除，分发改 switch；`TextElement::render` 三重 h-align 分支收敛为 `toQtAlignment()` + `hAligned()` 各一次。
- **附带勘误**：XSD 记载 cell 的 v-align/h-align 默认为 top/left，与代码实际默认 center/center 不一致——按代码为准修 XSD（改代码默认会破坏存量布局与金图基线）。
- **测试**：`test_diagnostics` 新增 3 用例（逐条上报、column 拒绝 baseline / row 接受、layout 属性非法保持默认），码表 32→33；`test_layout_behavior` 新增非法 cross-align 回退 stretch 行为钉。双栈 ctest 18/18。

## #5 "模板 parse 后不可变"纯注释约定

## #6 跨阶段隐式缓存契约

- **现状**：`GridNode::colWidths/rowHeights`（measure 写、layout 读，GridLayout.cpp:87-98,127-135）、`TextNode::contentRect`（layout 写、render 读，TextElement.cpp:225,263）、`Frame::m_boundingRect`。"measure 必须先于 layout"全靠注释，乱序调用读陈旧/零值无声失败。
- **方向**：至少断言化（Q_ASSERT 时序标记）；或讨论是否把缓存字段改为显式参数传递。

### 结论（2026-08，已实施）

策略：**能消除的契约连根消除，消不掉的用断言把违反变成显眼失败，已有守卫的不动**。逐一核实后三处的真实面貌与能力各不相同：

- **Text（假缓存，消除）**：`contentRect(rect, style)` 是纯函数，render 时输入（`node.rect`/`node.style`）均在手边——缓存本就不必要，且是全库唯一这么干的叶子部件（`ImageElement` 同族先例：render 现算）。删 `TextNode::contentRect` 字段，render 现算，layout 覆写退化为只写 `node.rect`。消除后乱序在结构上不可能，无需任何检查。原"读零值无声失败"（null 矩形 → 文本错位/消失且无警告）连根拔除。
- **Grid（真缓存，守卫 + 顺手修）**：列宽/行高是 measure→layout 的算法交接，layout 重测会改变 wrap 文本约束语义（行为漂移），消不掉。`GridNode` 加 `measured` 标志（measure 置位），`layout` 入口 `Q_ASSERT(gridNode.measured)`——把空 vector 越界 UB 变成 debug 下指向明确的断言失败，release 零成本。**顺手修不可重入**：layout 原就地改写缓存分配剩余空间（同一 measure 后二次 layout 会重复膨胀列宽），改为拷局部副本分配，缓存保持 measure 纯输出。
- **Frame（误报，不动）**：`paint`/`toImage` 已有 `m_boundingRect.isEmpty()` 守卫（Frame.cpp:206），本项列单属过虑。

**lazy<T> 泛型机制（讨论后暂不采纳，记录为备选）**：讨论中提出"延迟赋值类型 + 编译期开关（`using lazy<T> = T` 一键切零开销）"。方向认可（意图声明进类型、检查可开关），但当前不建：①适用真身仅 Grid 一处，为单点造泛型模板 + 双语义测试矩阵不划算；②Grid 主故障模式是空 vector 越界，发生在 vector 内部，lazy 包装挡不住，其实际保护等价于 bool 标志 + 断言；③Text 场景正确解是删缓存而非给缓存套仪器。若将来跨阶段缓存字段增多（出现第三、四个实例），有真实样本驱动时再设计泛型机制。

测试：行为等价性由全量回归背书（含金图逐像素），Grid 断言为 debug-only 不需新用例。双栈 ctest 18/18。

## #17 测试 mock Q_PROPERTY 样板

- **现状**：`tests/test_property_context.cpp:11-88` 两个 mock 类 82 行逐字式 READ/WRITE/NOTIFY 样板，结构完全相同仅基类不同。可宏/模板收一半。

### 结论（2026-08，接受现状，不改代码）

讨论裁决：**本条系扫描过虑，以"非土法"结案**。核实记录（防后人再捡）：

- **moc 约束决定可压缩上限远低于清单设想的"一半"**：模板路线死刑（Q_OBJECT 类不能是模板，moc 不支持）；宏路线上，moc 不是完整预处理器、不展开函数式宏——`Q_PROPERTY` 行与 `signals` 声明必须字面可见（否则元对象无属性、NOTIFY 解析失败），宏只能吞 getter/setter/成员三件：每属性 7 行省 4 行，8 个属性净省约 30 行，还需先花 ~10 行定义宏。
