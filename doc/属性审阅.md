## #1 `baseline`：文档 phantom 值，代码/ XSD / 文档三方不一致

### cross-align 的 baseline（row / column）

- **代码**：`src/element/layout/RowLayout.cpp:167-175`、`src/element/layout/ColumnLayout.cpp:165-173` 只识别 `stretch`/`center`/`end`，其他任何值静默按 `start` 处理，**无告警**。
- **XSD**：`crossAlignType`（broaditem.xsd:81-86）= `start|center|end|stretch`，无 baseline。
- **文档**：设计.md 的 row 表（:818）与 column 表（:783）均列了 baseline——文档独有。column 的交叉轴是水平方向，baseline 在语义上本不成立。

### text v-align 的 baseline

- **代码**：`TextElement.cpp:280-283`（换行路径）、`:304-307`（单行路径）只识别 `center`/`bottom`，其余一律按 top 绘制；`TextElement.h:43` 默认值写成 `"baseline"`，注释声称取值 `baseline|top|center|bottom`——baseline 与 top 走同一分支，是僵尸别名。
- **XSD**：`vAlignType`（broaditem.xsd:54-59）= `top|center|bottom`，text 默认 top。
- **文档**：设计.md text 表（:531）= `baseline|top|center`——有 baseline，反而缺代码真实支持的 `bottom`。

### 处置选项

| 选项 | 内容 | 代价 |
|------|------|------|
| A（推荐） | 删文档声明：设计.md 删两处 cross-align baseline 行；text v-align 改为 `top|center|bottom`；TextElement.h 默认值与注释改为 `top` | 行为零变化，纯文档/注释对齐 |
| B | 实现真 baseline：row 的 cross-align 支持跨子元素文本基线对齐 | QFontMetrics 级新特性，工作量大 |
| C | 仅记录为已知问题，不动 | 不一致继续存在 |

### 结论（2026-07 已执行）

A+B 组合：phantom 声明已全部删除（设计.md 两处 cross-align 表行、text 表 v-align/h-align 行、TextElement.h 默认值与注释）；同时经场景讨论（#6）确认 baseline 有真实需求，**转正立项**——作为 row 的 `cross-align` 新值实现，设计要点见 #6。

## #2 `v-align`/`h-align` 取值漂移：漂移在文档层，代码层其实一致

审阅时假设"text 与 cell 各有一套枚举"，核实后推翻：

- **代码层一致**：`TextElement.cpp` 与 `CellElement.cpp:61-63` 的 v-align 都是 `center`/`bottom` 两分支 + 默认 top；h-align 都是 `center`/`right` 两分支 + 默认 left。**代码没有漂移**。
- **XSD 层一致**：text 与 cell 共用 `vAlignType`/`hAlignType`（broaditem.xsd:271-272 vs :391-392）。
- **文档层漂移**：设计.md text 表（:531-532）声称 `v-align: baseline|top|center`、`h-align: left|right|center|decimal`；cell 表（:864-865）声称 `v-align: top|center|bottom`、`h-align: left|center|right`。两张表各错一处。

### 附带发现：`h-align="decimal"` 同样是 phantom

- `decimal` 在 `src/` 中**零出现**（grep 无匹配），XSD `hAlignType` 也不含。设计.md :532 是唯一声称它存在的地方。
- 小数点对齐对监控铭牌数值列是真实价值，但它从未被实现，审阅时"懂场景的设计"的判词需收回——是"懂场景的文档"。

### 处置选项

| 选项 | 内容 |
|------|------|
| A（推荐） | 设计.md 两张表统一改为与代码/XSD 一致（`top|center|bottom`、`left|center|right`），decimal 移入"未来候选" |
| B | A + 真正实现 decimal 对齐（按小数点位置对齐数值列，TextElement 渲染层工作量） |

### 结论（2026-07 已执行）

按 A 执行：设计.md text 表已改为 `top|center|bottom`、`left|center|right`。decimal 经专门论证（#6）后确认**不实现**——text 级属性会导致跨层耦合，容器级做法成本高于场景收益；作为"已论证、暂不实现"候选登记。

## #3 缺"元素位置决策链"完整推导文档

一个 `<text>` 的最终位置由多层共同决定：父容器 `cross-align`（可能拉伸）→ 显式 `width`/`height` 豁免 → `<cell>` 的 `v-align`/`h-align` → text 自身的 `v-align`/`h-align`（content 对齐）。设计.md :869 只澄清了 cell 与 text 的边界，没有任何一处把完整优先级链推导一遍。

- **性质**：纯文档工作，不改代码。
- **建议落点**：设计.md「布局」节新增小节，按"谁决定尺寸、谁决定位置、显式尺寸在哪一层豁免"逐层推导，附一个 column > row > text 的完整例子。

## #4 命名问题（三小项）

### 4a `under-line`

- **现状**：代码（`TextElement.cpp:17,81`）、XSD（:276）、设计.md（:535）三方一致使用 `under-line`。
- **问题**：underline 是一个词，连字符位置别扭；但三方一致意味着改名是纯破坏（XML 是现场实施人员的 API）。
- **选项**：A. 保持现状，文档注明"历史命名，不改为美"；B. 引入 `underline` 别名并废弃 `under-line`（BI-P-006 级别的 deprecated 通道已有先例）。
- **结论（2026-07 已执行）**：因尚未 release，改名窗口存在，用户拍板**直接改名**——`under-line` → `underline`，不留别名。已改：`TextElement.cpp`（6 处）、`TextElement.h` 注释、`broaditem.xsd`（4 处）、`doc/设计.md`（3 处）。测试/示例 XML 无使用，无需联动。

### 4b grid 的 `space-row`/`space-column` 与 row/column 裸 `space` 不对称

- **现状**：grid 有方向变体（broaditem.xsd:838-840，设计.md），row/column 只有单方向 `space`。
- **语义核实**（`GridLayout.cpp:44-54`、`:119-124`）：`space` 为双向兜底值，`space-row`（行间距）/`space-column`（列间距）按方向覆盖，`optional.value_or(m_space)` 回落——与 CSS Grid 的 `gap`/`row-gap`/`column-gap` 同构，属"简写+方向展开"惯例（同 `margin`/`margin-left`）。
- **结论（2026-07 关闭）**：经讨论确认非问题，关掉不动，不改任何文件。

### 4c `width="-1"` 哨兵值

- **代码**：`SizedElement.cpp:20` 解析缺省为 -1；`RowLayout.cpp:168`、`ColumnLayout.cpp:166` 以 `< 0` 判断"未显式指定"——-1 是**纯内部哨兵**。
- **XSD**：width/height 均为 `nonNegativeDouble`（broaditem.xsd:280-281、:318-319），**不允许书写 -1**——XSD 已正确。
- **文档**：设计.md :540-541 把 `-1 表示未指定` 写成面向用户的属性语义，误导（暗示用户可以写 -1）。
- **结论（2026-07 已执行）**：设计.md 全部 4 处（text 与 image 的 width/height 行）改为"省略表示未指定"。

## #5 `content` 三重身份的例外

- **现状**（设计.md :239、:311、:552）：`content` 既是 `<text>` 普通字面量属性，又是保留属性走专用通道；`b:content` 回退行为与通用绑定不同（回退标签内文本而非默认值）；渲染优先级 `content` 属性 > `b:content` > 标签内文本（属性优先于标签体，反 XML 直觉）。
- **评估**：三条例外服务历史兼容，理解成本可控，有诊断码托底（BI-P-014）。
- **选项**：A. 保持行为，设计.md 补一段集中说明三个来源与优先级（推荐）；B. 简化模型（破坏性，不建议）。
- **历史动机**（2026-07 用户澄清）：早期曾打算仿 Vue 模板插值在标签体内做绑定，因与其他属性的 `b:` 前缀绑定不统一而否决，遂引入 `content` 属性——它是文本内容进入"字面量 | 绑定"统一模型的载体，**不是冗余设计**。
- **结论（2026-07 已执行）**：按 A 执行。设计.md `<text>` 节新增「内容来源与优先级的设计理由」小节：content=字面量载体、b:content=绑定、标签体=默认文本+绑定回退；插值否决史一并记录。

## #7 cell 拉伸子部件的文档误述（#3 写作期间发现）

- **文档（旧）**：设计.md cell 小节称"当cell被拉伸时，其子部件也会被拉伸（已显式指定 `width`/`height` 的子部件除外）"。
- **代码**：`CellElement.cpp:66-73` 子部件矩形 = 固有尺寸（钳制到 cell 内容区），**不存在拉伸**；cell 只按 `v-align`/`h-align` 定位堆叠块。
- **结论（2026-07 已执行）**：cell 小节描述已按代码现实改写（cell 不拉伸子部件，块整体定位、超出钳制）；新「位置决策链」小节亦按此记述。

## #6 align 类属性取值集讨论（由 #1 引出）

三层对齐模型（容器主轴空间分配 / 容器交叉轴盒子放置 / 叶子盒内内容放置）本身成立，逐层讨论取值集后的**决策记录**：

| 取值 | 结论 | 理由 |
|------|------|------|
| `main-align` 全家（start/center/end/space-between/space-around/space-evenly） | ✅ **保留**（2026-07 用户确认） | space-between 是"标签左、数值右"刚需；space-around/space-evenly 用户确认为典型场景 |
| `cross-align` start/center/end/stretch | ✅ 保留（现状） | 完备 |
| `baseline` | ✅ **已实现**（2026-07） | 作为 row 的 cross-align 新值实现；场景二合一：① 大数值+小单位混排 ② 非文本元素+文本并排（图标/状态灯底边落在文字基线上，用户提出） |
| `decimal` | ❌ **不实现**（2026-07 用户确认） | 论证见下；作为"已论证、暂不实现"候选登记，phantom 声明已随 #2 删除 |

### baseline 实现设计要点（立项依据）

- **非文本元素的基线语义**：参照 CSS flexbox 规则——无基线元素以其**下边缘**（含 margin 底边）作为基线参与对齐；不提供基线的元素自动退化为底边对齐，行为可预期。
- **基线钩子**：measure 阶段元素可提供自身基线位置（`TextElement` 报 ascent，其余默认报内容高度）；`RowLayout` 按 `cross-align="baseline"` 时以此为参照定位。基线是单元素局部信息，无需跨兄弟协调。
- **作用域**：仅 row 的 cross-align（水平主轴、垂直交叉轴）；column 交叉轴为水平方向，无 baseline 语义。

### decimal 不实现的论证（2026-07）

- **text 级做法（否）**：`h-align="decimal"` 的对齐参照系存在于兄弟元素之间，单个 text 盒子内部无定义；实现它要求父容器窥探叶子文本内部结构，破坏"cell 管位置、text 管内容、容器不看叶子内部"的分层（用户指出"影响范围不局部"，论证成立）。
- **容器级做法（有先例但仍不划算）**：decimal 对齐本质是容器协调多个子元素测量值，与 `main-stretch` 同类——可做 column/grid 级属性（如 `decimal-align="true"`），子元素暴露整数宽/小数宽度量钩子。但只对单行数值文本有意义、与 `wrap` 互斥、小数点字符约定、非数值内容退化规则等语义表面积大，场景频率低于 baseline（`space-between` + 右对齐已覆盖大部分观感）。
- **未来重启条件**：若有真实用户提出数值列精确比对需求，按 main-stretch 先例以容器级属性立项，预估半天工作量。
